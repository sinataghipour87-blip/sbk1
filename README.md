# SBK1 + Freqtrade

SBK1 remains the TypeScript/React analysis and monitoring application. The eight-member council is the sole source of entry direction; the central post-council controller validates the council report and checks live data, executable spread, ATR-based per-candle volatility, entry/stop/target geometry, price deviation, holding-horizon evidence, and risk allocation without generating a market-direction prediction or requiring an additional predictive-model vote. It prepares an authorization for the council's unchanged direction only when every execution gate passes. Freqtrade is the sole owner of order placement, fills, open positions, protective stop-losses, and trade persistence. The Node service validates the versioned `sbk1.freqtrade.signal.v3` contract and serves an authenticated pull queue to the Freqtrade strategy. The signal runner and strategy consumer require `dry_run=true`; `SBK1_LIVE_ENABLED` does not enable this path. The legacy manual UI entry endpoint returns HTTP 410, and the dashboard's signal card is display-only. The browser never calls the Freqtrade API.

The dashboard does not calculate council votes. The server runner publishes its authoritative report and decision status through `/api/decision/stream`; the council panel, chart, and Auto-Pilot status display that report. Auto-Pilot is controlled through `/api/decision/auto-pilot` and gates new entries only; the runner continues managing approved exits when it is off. Manual LONG/SHORT buttons submit intents through `/api/decision/manual-entry`; they do not authorize an entry themselves. The server evaluates the next eligible closed 15-minute candle through the same council, post-council, risk, and Freqtrade signal-queue path. Both endpoints require a running Freqtrade instance with `dry_run=true`, `force_entry_enable=false`, and a disarmed SBK1 kill switch. Outside the local-development exception below, write requests also require a valid `ADMIN_TOKEN`. Auto-Pilot resets to off after server restart. No browser-only position is created, and live trading is unsupported.

For local development only, set `SBK1_LOCAL_DEMO_AUTH_BYPASS=true` to let the manual LONG/SHORT and Auto-Pilot endpoints accept requests without a browser admin token. The bypass is limited to non-production processes bound to a loopback address and requests whose client and Host/Origin are local; all other admin routes remain protected. It does not bypass Freqtrade `dry_run=true`, `force_entry_enable=false`, kill-switch, council, or risk checks. Keep the flag false outside local development. LIVE remains unsupported and disabled.

The chart's display-only live feed uses Bybit linear public trades first, then a fresh ticker from the configured Bybit Freqtrade snapshot, and finally Binance Futures trades when both Bybit sources are stale. During Binance failover, the chart loads validated Binance candles before displaying Binance's live price and hides indicators, predictions, position overlays, and trade levels calculated from Bybit data. When Bybit recovers, the chart returns to its Freqtrade candles and restores those overlays. Both public streams reconnect automatically and reject stale prices; if neither source is fresh, the chart reports the outage instead of presenting an old price as live. These feeds do not supply trading decisions or orders, which remain on the authenticated Freqtrade snapshot and signal path. No networked feed can guarantee uninterrupted connectivity during exchange, network, or service outages.

This integration is **not declared production-ready**. The checked-in Freqtrade configuration is a dry-run template; no live exchange order, fill, restart recovery, or end-to-end deployment was executed in this workspace.

### Council ownership and the single post-council control

The eight council members own direction and domain analysis. After quorum, the central controller does not rerun the council's analysis or produce a second direction. It validates the report against exactly eight unique member IDs, recomputes vote totals and the 5-of-8 direction, and checks live data, reference-price deviation, executable spread, direction-consistent entry/stop/target levels, stop distance, reward/risk, and risk allocation. It does not require specialist members to vote, nor does it require a predictive-model ensemble or use model disagreement as a veto. The quorum remains 5-of-8; missing or invalid execution evidence fails closed.

Member source records are persisted per snapshot with the input values, source timestamps, module status, checks, rationale, and final vote. A module is not marked `AVAILABLE` merely because it returned a non-null object: evidence availability also checks the fields required by that module. Macro and blockchain sources use their own observation timestamps and allowed freshness windows; they do not have to share the candle timestamp. Derived heuristics are identified as such and are not promoted to measured or calibrated signals.

Central risk sizing selects per-trade margin between 2% and 10% of equity and leverage between 5x and 25x, based on available balance, the configured stake ceiling, the authorized stop distance, and the risk budget. The controller uses the largest feasible margin within those bounds and chooses leverage to keep stop-loss exposure within budget; it rejects a trade if the minimum margin/leverage would breach the remaining risk budget or available balance. `SBK1_SIGNAL_RISK_BUDGET_PCT` is the per-trade equity-risk ceiling (default 10%, hard maximum 10%); portfolio open risk is capped at that amount multiplied by Freqtrade's positive `max_open_trades`. The margin and leverage ranges are boundaries, not targets; they do not override risk or exchange limits. Freqtrade uses `stake_amount: "unlimited"` only to enable the custom stake callback; every accepted SBK signal carries a calculated absolute margin cap, and the strategy returns zero stake if the resulting exchange leverage is below 5x. The strategy applies the signal's selected leverage up to Freqtrade's reported exchange maximum; it does not accept Freqtrade's default proposed 1x as a cap. `SBK1_SIGNAL_MAX_ATR_PCT` (default 2%, maximum 5%) is a hard execution gate on ATR as a percentage of the live Last price for each configured candle; higher or unavailable ATR blocks entry. Freqtrade's UTC-day closed-trade history enforces `SBK1_SIGNAL_DAILY_LOSS_LIMIT_PCT` (default 10%, maximum 10%). Existing open risk is reserved from both budgets; open trades without a matching SBK signal and protective stop block new entries. The controller sends the final absolute dollar risk and margin cap to Freqtrade, which sizes once against the actual entry-to-stop distance rather than applying the percentage a second time. `SBK1_SIGNAL_MAX_STAKE_QUOTE` is an additional hard cap on per-trade margin. The 10% risk ceiling and 25x leverage are upper bounds, not targets or a claim those settings are suitable.

Brain12 and Brain13–21, SB3/SB4, the legacy analysis pillars, anti-tilt gate, and news shock firewall are explicitly classified as unwired/legacy rather than active council or central-control producers. In particular, Brain16's drawdown-lock state is unavailable, and other lifecycle/latency brains lack verified live measurements; none of these outputs is treated as an operational veto or leverage signal. SB5 remains the council coordinator. The `NewsShockFirewallService` has placeholder calendar assumptions, so its report is not an authoritative central execution gate.

### Public Bitcoin on-chain evidence

The council's existing whale/on-chain member reads sampled confirmed Bitcoin outputs from mempool.space and falls back to Blockstream's public API if the primary source fails; basic requests need no API key. When the server signal runner starts, it prefetches in the background and refreshes every 60 seconds, sharing an in-flight refresh with council requests. Each request has a 2.5-second default timeout, one bounded retry, and a maximum configurable timeout of 3 seconds. It checks three recent blocks, requests their first transaction pages with rate-limited starts, keeps a 60-second refresh cache, and retains the last successful sample for up to 20 minutes during provider errors. Bitcoin samples are accepted only up to the configured 20-minute maximum age. Coverage is `SAMPLED`—it is not a complete whale-flow feed. `SBK1_WHALE_MIN_TRANSFER_BTC` (default 10), `SBK1_WHALE_BLOCK_SAMPLE_COUNT` (default 3, maximum 10), `SBK1_WHALE_REQUEST_TIMEOUT_MS` (default 2500, maximum 3000), and `SBK1_WHALE_MAX_AGE_MS` (default and maximum 1200000) tune sampling and provider freshness. A sampled output is context only: it does not identify an owner, exchange, or trade direction. A single observed provider and non-directional sample do not meet member 6's two-source directional quorum, so this evidence cannot by itself produce a directional vote. Bitcoin block production is not continuous, so polling cannot guarantee a new confirmed block or a directional whale signal. The runner supplies its current BTC price for an optional USD estimate; without a usable price the estimate is null.

An output is an observed transaction output, not a proven transfer between distinct owners: change outputs, self-transfers, exchange attribution, and buy/sell intent are not inferred. The member stores these observations as context and does not infer a vote direction from them. Missing, stale, or malformed evidence, or fewer than two valid directional measurements, causes abstention. Whale Alert remains an optional fallback when `WHALE_ALERT_API_KEY` is configured. Blockchain.com Explorer's currently published OpenAPI schema exposes `/x402/*` paid routes rather than a verified free block/transaction route, so it is not activated. Etherscan V2 uses `chainid=1` and may return native ETH and configured ERC-20 transfers as distinct evidence. If Etherscan fails or yields no qualifying transfers, the keyless fallback tries PublicNode and then 1RPC, checking chain ID 1, the latest 50 blocks, 12 confirmations, and a five-minute freshness limit. ERC-20 evidence is not filtered out or relabeled as native ETH. `SBK1_ETHERSCAN_WATCH_ADDRESSES` is still required and must contain operator-verified addresses; without a usable watchlist, the member abstains. Coin Metrics `AdrActCnt` remains only a Bitcoin network activity metric, not whale flow.

Keyless on-chain paths are available for ETH, SOL, XRP, and BNB, but none is a global whale feed: each needs a configured, independently verified destination watchlist and positive native-asset threshold. SOL uses finalized standard Solana JSON-RPC transactions, limited to recent activity and bounded requests; Helius is optional. XRP uses XRPSCAN public transaction data. BNB uses public BNB Smart Chain JSON-RPC with chain ID 56; BscScan V2 is an optional keyed supplement. Non-ETH member 6 catalogs only the providers currently declared for each chain (BTC: 2; SOL: 3; XRP: 1; BNB: 3). The live flow selects one provider and does not treat an unqueried fallback as a second healthy source. Raw transfer samples are context-only and do not count as direction-bearing signals. Public RPCs/RSS endpoints have no project-controlled SLA and can rate-limit or fail; absent watchlists, stale observations, or fewer than two direction-bearing metrics cause abstention rather than use of guessed addresses or another asset's data. All watchlist variables are documented in `.env.example`; the operator must populate them with verified exchange addresses and set the matching `SBK1_WHALE_MIN_SOL`, `SBK1_WHALE_MIN_XRP`, and `SBK1_WHALE_MIN_BNB` native-asset thresholds. Never use unverified/example wallets.

For news, the adapter keeps the verified Bitcoin Core, Ethereum Foundation, Solana News and Solana Status feeds, and adds free U.Today and Cryptonews RSS coverage. The added aggregator feeds are keyword-filtered by the full asset name or explicit asset context (for example, `Solana` or `BNB Chain`); standalone ambiguous `SOL`/`BNB` headlines are rejected. Ripple Insights and the proposed BNB Chain RSS remain disabled because their endpoints failed validation. RSS availability does not guarantee enough fresh, asset-specific headlines to vote; insufficient evidence abstains.

### Council source registry and staged integrations

`npm run verify:council-sources` emits a `sourceRegistry` for on-chain, macro, news, derivatives, options, order-book, trend, and trade-flow sources. Each entry reports its provider, endpoint, data type, symbol, source-response timestamp, receipt time, maximum age, health, and failure/telemetry reason. `UNOBSERVED` means the current adapter does not provide endpoint-level telemetry; it is not reported as healthy. FRED/ECB daily or periodic observations are explicitly context-only and are not tagged as real-time sources. FRED `DTWEXBGS` is identified as a broad-dollar index, not ICE DXY; TradingView `TVC:DXY` remains explicitly a CFD proxy.

`COUNCIL_MEMBER_SOURCES` records exactly four ordered, ETH-scoped providers for each of the eight members. BTC, SOL, XRP, and BNB also have pair-scoped source checks for members 1-5, with market identifiers resolved from public exchange catalogs. Their observations are written to the corresponding pair-specific council room, not shared with ETH. Members 1 and 3 need two valid sources to vote; member 2 uses one CVD venue with a minimum of five aggressor-classified trades in five minutes and a 60-second newest-trade limit; member 4 needs two valid derivative sources. For member 2, Bitstamp's public transaction feed does not expose aggressor side, so it is recorded but cannot count as CVD-valid.

Member 5's currently live-verified asset-specific options catalog is intentionally incomplete where venues do not publish validated listings: BTC has four entries, SOL three, XRP two, and BNB one. Mark-price/IV-only data is context, not a directional source; the member votes only with at least two valid directional sources and otherwise abstains. Run `npx tsx scripts/verify_council_asset_sources.ts` to live-check members 1-5. Members 6-8 do not yet have equivalent non-ETH source-check catalogs; pair-aware modules alone are not evidence of four verified sources.

ETH records are isolated under `data/council-members/ETH_USDT_USDT/member-NN.jsonl`. Normalized source measurements and source-health evidence are saved with each member's pair-scoped room record. Member 5 accepts timestamped option OI ratios and a put-minus-call IV skew of at least 0.02 (two volatility points). Binance `/eapi/v1/mark` uses response-received time, explicitly not provider time; current live Binance and OKX matched call/put IV values were equal, so IV parity is context-only and those payloads are not counted as directional sources.

Member 6 labels its two intended direction metrics as non-conclusive heuristics: seven-day Ethereum stablecoin supply changes beyond ±0.5%, and more than 1,000 ETH of gross staking-deposit contract inflows in a confirmed, approximately 24-hour window. The latter is measured from the official deposit contract's `DepositEvent` logs through PublicNode `eth_getLogs`; it is gross inflow, not net balance change, because exits are not subtracted. Both metrics must be valid; conflicting or ambiguous metrics resolve to NEUTRAL. PublicNode `eth_feeHistory` and DefiLlama daily Ethereum DEX volume are context only. DEX volume is reported with one- and seven-day changes but does not independently imply buying or selling. These four sources require no API keys. The member's confidence is capped at 40%, and its directional vote contributes 0.4 toward the council's five-weighted-vote threshold; it only casts a ballot when both heuristics agree.

Member 7 uses a low-confidence daily macro heuristic with a 40% confidence ceiling. Its fourth slot is another public FRED CSV group, explicitly not an independent provider from the first FRED source; Yahoo Finance is unofficial. Daily inputs allow seven days and weekly WALCL allows fourteen days. Stooq remains documented as HTTP 403 but is no longer a voting source.

Member 8 filters the whole word `ETH`, `Ethereum`, or `Ether` in title, description, or categories over 24 hours; headlines in the latest six hours receive twice the weight. The four voting feeds are Decrypt, The Block, CoinDesk, and Google News RSS. Google News is an unofficial aggregator; the article's source tag, not Google, is used for publisher coverage. Cointelegraph remains a live diagnostic feed but is not in the four vote slots. At least two actual publishers must each provide a relevant headline. This environment has neither Torch nor the pinned sentiment model, so member 8 uses the explicitly low-confidence `lexicon` fallback rather than silently abstaining for a missing model. Publication timestamps without an explicit timezone are not used.

The public FRED graph CSV works without a key. Cboe VIX and Yahoo chart observations are validated against publication timestamps rather than treated as live ticks. Three consecutive Bitfinex requests returned 100 recent ETH trades, with the newest trade under three seconds old and at least five classified trades in the five-minute window; it replaced Bitstamp in member 2's fourth slot. The Binance mark endpoint returned 574 ETH option contracts and is registered with the explicitly approved response-time fallback. CryptoSlate returned HTTP 403 and is not registered.

Run `npm run verify:council-eth-sources` for live response and data-level checks. Its table separates HTTP health from validity of fields, units, plausible values, and timestamps, prints live source-derived member votes, and compares the four ETH hourly closes (warning above 0.5% spread). It also reports total RSS items, latest dates, relevant ETH-story counts for 6/24/72 hours, five latest titles, timezone/date parse failures, and current model/Torch availability. HTTP 403/451, missing keys, and provider RPC errors remain explicit; the verifier does not turn them into successful data. `sourceId` identifies the source used and `fallbackSourceId` identifies a lower-priority source when failover is active. The verifier's live exit code may be nonzero when a source is unavailable or below its data requirements.

## Historical data and calibration status

- Central candle research is separate from member 1's vote. For the execution path it uses only completed candles from the configured Freqtrade DataProvider snapshot (up to 1,500 candles), and records exchange, market type, pair, timeframe, and source timestamp. Central control requires exact exchange/market/pair/timeframe identity and fresh source data; missing or mismatched identity blocks entry. The standalone `npm run probe:historical-candles` still probes Binance public data and is advisory only; its output cannot authorize a trade on another venue. Research compares 12-bar candle shape plus 48-bar trend/volatility/relative-volume context, with an 85% similarity threshold. Its chronological 70/30 walk-forward split reports 7, 15, 30, and 60-minute evaluation horizons, rounded up to whole candles (for example, 7 minutes on 15-minute bars is measured as 15 minutes). Test starts are independently spaced for each horizon with non-overlapping pattern-plus-outcome windows. Each forecast needs at least three matching training windows; metrics require 20 out-of-sample forecasts. After council quorum, central control selects the longest actual horizon up to 60 minutes only if costs are configured, the report is fresh and market-matched, and the horizon has at least 20 forecasts, positive mean net return, at least 52% net wins, a family-wise 95% Wilson lower confidence bound above 50% across the four tested horizons, and cost-adjusted reward/risk of at least 1.1; otherwise entry is rejected. The confidence bound is more conservative than an observed win-rate cutoff, but it is not a substitute for empirical calibration across independent market regimes; aggregate timeframe results do not prove an edge for the individual live pattern. The chosen horizon and per-horizon reasons are persisted in the execution audit and shown in the council panel using the authenticated `/api/freqtrade/execution-audit` endpoint. Freqtrade enforces it as a time-based exit when its strategy loop evaluates the trade; exact-second execution is not guaranteed. Current net returns include configured taker fees and slippage only, not funding, market impact, position-size effects, or actual stop/target fills. Set both `SBK1_PATTERN_TAKER_FEE_BPS` and `SBK1_PATTERN_SLIPPAGE_BPS` to realistic per-side estimates; missing or invalid values block execution.
- Audit real downloaded Freqtrade Feather OHLCV before backtesting with `.venv/bin/python scripts/audit_freqtrade_market_data.py freqtrade/user_data/data/bybit/futures/BTC_USDT_USDT-15m-futures.feather --timeframe 15m`. It checks timestamp order and cadence, missing intervals, finite values, OHLC geometry, future timestamps, and counts incomplete candles separately. It does not establish that historical order-flow features or SBK1 decisions are available.
- In the 2026-10-11 workspace audit, Bybit returned 35,109 BTC/USDT:USDT 15m candles from 2025-10-11 through 2026-10-11; the OHLCV audit found no gaps or malformed rows. Freqtrade's SbkSignalStrategy backtest on that history produced zero trades because the live external-signal queue is intentionally not consumed in backtesting. Zero trades is not a performance result.
- Browser `localStorage` is not a training source. The server-side operational archive stores runner decisions, contemporaneous feature snapshots, code/model/feature versions, lifecycle events, and closed-trade PnL/fees/exit reason from authenticated Freqtrade RPC, linked by signal ID and a positive trade ID. Only complete Freqtrade-confirmed outcomes enter probability training; the existing calibration engine still requires at least 40 training samples, 20 validation samples, and a dynamically sized out-of-sample set (at least 200), including both win and loss outcomes. Until these minima are met, the UI reports “نمونه ناکافی” and the server runner rejects entry candidates that lack verified calibration.
- Until enough timestamped SBK1 decisions, contemporaneous features, and authoritative Freqtrade outcomes are collected and validated, `/api/backtest/run` returns `HISTORICAL_SIGNALS_UNAVAILABLE`, the probability UI reports insufficient samples, and the server runner remains fail-closed for new entries.
- The 11-brain dashboard is only a registry of UI processor labels. Runtime health, votes, CPU, latency, and calibrated accuracy are not instrumented there and must not be inferred from its display.

## Signal and state ownership

1. The server signal runner validates the eight-member council's vote totals, quorum, and selected direction, then passes that unchanged direction to the central execution controller. The controller is not a predictor: it checks fresh/live market data, price deviation, spread, direction-consistent entry/stop/target levels, stop distance, reward/risk, and risk-budgeted position sizing. It does not require a second predictive ensemble or independently select LONG/SHORT. Missing or invalid execution evidence fails closed. Freqtrade remains the only order executor, and the path remains DRY_RUN-only.
2. `POST /api/hunter/execute` returns HTTP 410; heuristic UI analysis cannot authorize an entry. Only the server decision runner can create a council-authorized entry contract after execution and portfolio-risk checks. Freqtrade remains the only order authority.
3. Authenticated polls to `GET /api/freqtrade/signals` serve entries only when Freqtrade is running with `dry_run=true`, `force_entry_enable=false`, and matching market configuration. The managed launcher rejects `dry_run=false`; `SBK1_LIVE_ENABLED` cannot enable LIVE. For bridge testing, `POST /api/freqtrade/dry-run-test-signal` is an explicit test-only fixture path and requires the fixture flag plus Freqtrade `dry_run=true`.
4. Freqtrade strategy callbacks send status updates to `POST /api/freqtrade/signals/:signalId/status`; the admin-only `GET /api/hunter/signals/:signalId` is a signal audit view. Authenticated Freqtrade RPC `/status`, `/trade`, and paginated `/trades` are used for trading-state reads and closed-trade confirmation. Admin-only archive endpoints expose the server-side records.
5. `data/sbk1-operational-trade-archive.json` (overridable with `SBK1_TRADE_ARCHIVE_PATH`) is an atomic, restart-persistent SBK1 audit projection. It excludes test fixtures, stores the decision/features and code/model versions at signal creation, retains lifecycle-reported trade IDs and fill updates, and records PnL, fees, and exit reason only after authenticated Freqtrade RPC confirms the closed trade, matching signal tag, pair/direction, and valid trade ID. Every RPC snapshot is tagged `DRY_RUN` or `LIVE`; dry-run results remain simulations, not evidence of exchange fills. The archive is not a second trading database and never gates a trade. It is single-process/file-backed, so deployments must use one SBK1 writer and durable storage. Freqtrade's database remains the source of truth for trades, orders, balances and positions.
6. `UNKNOWN_IN_FLIGHT` signals remain visible to the strategy but quarantined from entry. After restart or a bridge timeout, the strategy reconciles the signal tag, pair, direction, and persisted Freqtrade order/fill state before advancing lifecycle; without an authoritative match it remains unknown and is never retried.

## Market-data and model truth policy

- Live OHLCV uses completed candles only. The Bybit and KuCoin readers validate finite OHLCV geometry, monotonic interval timestamps, and remove the still-forming candle; a missing interval or invalid timestamp rejects the feed. Candle event/close time, response receipt time, measured request latency, symbol, market type, and timeframe remain distinct.
- Bybit linear-futures `BTCUSDT` is primary. KuCoin `XBTUSDTM` can be used only after base asset, settlement, contract type, and timeframe compatibility checks pass. Spot, synthetic candles, and stale cache entries are never substitutes for live futures data. Failed or unproven provenance is unavailable, not zero or neutral.
- Price roles are not interchangeable: Last is the execution reference, Mark is the risk/stop/liquidation reference, and Index is the underlying benchmark. A missing required price is returned as unavailable; another price type is never substituted. Divergence cannot be considered safe unless both Last and Mark are fresh and valid.
- Order-book imbalance, Funding, Open Interest, and trade flow are valid only when the supporting live feed provides them with provenance. Unsupported or missing metrics remain unknown. Backtests must use only information available at or before each simulated event; use completed historical bars and do not forward-fill future values.
- Wave outcome probabilities are directional continuation rates, not win probabilities or trade-duration instructions. The dashboard reports 5m, 7m, 15m, 30m, and 60m horizons only after at least 20 comparable resolved observations; outcomes are omitted if the next observation arrives more than 90 seconds after the target horizon. Historical Wave DNA matching excludes benchmark, manual-estimate, legacy, and exit-time-only records. No such record currently has verified entry-time provenance, so the Wave DNA matcher must remain `UNAVAILABLE` until genuine entry features and confirmed outcomes are archived together.
- `scripts/predictor.py` is a heuristic moving-average/price-change/order-imbalance analysis, not a trained or calibrated probability model. `scripts/garch_volatility.py` is a fixed-parameter, unfitted volatility approximation, not a validated forecast. Both explicitly return `tradeEligible: false`; missing input and process failures do not produce directional, confidence, regime, or target fallbacks. Their definitions are analysis-only and must not differ between backtest, dry-run, and live signal eligibility.
- Server analysis uses canonical OHLCV tuples in `[open, high, low, close, volume]` order; candle event timestamps remain separate metadata. Signal candidates require fresh, structurally valid Freqtrade market data, an allowed analysis result, a confirmed trigger, and verified calibration. Insufficient samples block new entries.
- MultiBrain widgets render diagnostics; the server runner separately passes the ensemble report into its full decision pipeline. Only independently validated model records can contribute to entry authorization, and none currently qualify. Estimated CVD/OBI-derived features are labeled non-empirical, missing whale-transaction counts remain unavailable, and activity monitoring reports only recorded pulses without synthesizing health, latency, or restart status.

## Safety controls and order lifecycle

- SBK1 starts with its server-side kill switch engaged unless a valid persisted state says otherwise. Engaging it blocks new SBK1 signals, stops SBK1 auto-trade, and cancels unclaimed queued signals. It does **not** cancel exchange orders already submitted by Freqtrade or close/modify open positions; the API reports those as unaffected. Reconciliation and position management remain Freqtrade's responsibility. State is persisted in the ignored runtime file `database_kill_switch.json`.
- The mode endpoint rejects LIVE, the managed launcher requires `dry_run=true`, and signal delivery additionally requires `force_entry_enable=false`. The optional dry-run fixture is a separate admin-only test path, refuses delivery unless Freqtrade RPC verifies `dry_run=true`, and never turns off Freqtrade's force-entry guard. Freqtrade's example config listens on loopback with authentication enabled and force-entry disabled. Never expose the Freqtrade management API publicly; configure credentials only in the private Freqtrade deployment.
- Freqtrade applies the contract `stopLoss` through `custom_stoploss` and the exact `takeProfit` threshold through `custom_exit` (`sbk_take_profit`), with `confirm_trade_exit` checking the threshold before accepting that exit. SBK1's ordinary exit intent is a separate authenticated exit signal; Freqtrade is still the only component submitting the exit order. A kill switch blocks new entries and reports open Freqtrade positions, but does not claim to close or cancel existing positions/orders.
- Cross-origin browser access is denied unless the request is same-origin or its exact origin is listed in `SBK1_ALLOWED_ORIGINS`. Admin and bridge routes require server-side authentication. Keep `.env`, Freqtrade configuration, bridge tokens, and API credentials private.
- Order states are `CREATED → SUBMITTED → ACKNOWLEDGED → PARTIALLY_FILLED → FILLED`, with explicit `REJECTED`, `CANCELLED`, and `UNKNOWN_IN_FLIGHT` branches. Unknown submissions must be reconciled with Freqtrade/exchange before retry; repeated signal IDs are idempotent. Actual fill prices, fees, protective orders, orders, and positions are only confirmed from Freqtrade/exchange state, never from a local estimate.

The Node signal store is single-process and file-backed. Run one SBK1 writer, place the store on durable storage, and use a private network for the Node-to-Freqtrade bridge. Multi-instance deployments require a transactional shared store/queue before enabling this integration.

- The initializer reads `.env.example` and `freqtrade_integration/config.example.json`, checks that the exchange (`bybit`), futures market, pair (`BTC/USDT:USDT`), timeframe (`15m`), strategy (`SbkSignalStrategy`), and dry-run settings agree, then creates `.env` and `freqtrade/user_data/config.json` with mode `0600` on POSIX. It generates independent cryptographically random admin, bridge, RPC, and JWT credentials without printing them. It refuses to overwrite either private file; back up and reconcile existing settings manually. Review both private files, keep `dry_run: true`, and do not add exchange API keys for this local integration test. On Windows, use `py -3.12 -m venv .venv` and `.venv\Scripts\python.exe` / `.venv\Scripts\pip.exe`; restrict the private files' ACLs to the service account.
- The optional fixture is independently fixed at 1x leverage, a maximum 1% fixture risk budget, and stake no greater than 100 USDT; Freqtrade's `max_open_trades` is 1. It does not use the normal signal leverage cap. The fixture still requires `SBK1_DRY_RUN_FIXTURE_ENABLED=true`, fresh Freqtrade market data, authenticated RPC confirmation of dry-run, no open trades, force-entry disabled, and a disarmed kill switch. Turn the fixture flag off afterward. The execution integration remains DRY_RUN-only and is not production-ready.
- `npm run sbk1` starts the complete managed stack: it validates private settings and strategy discovery, detects occupied ports, acquires a single-instance lock, starts Freqtrade and waits for authenticated RPC health before starting SBK1 API/UI. The strategy retries bridge polling and market snapshot publishing until SBK1 is available. `npm run sbk1:check` validates without starting services; `npm run sbk1:status` reports SBK1 API and authenticated Freqtrade RPC health separately. `npm run dev` starts only the SBK1 service. Ctrl+C requests graceful shutdown of both managed services. If either child exits unexpectedly, the supervisor stops the other and exits nonzero. Existing listeners are detected and never killed automatically; identify and authorize any stop yourself.
- After setup, validate with `npm test`, `npm run lint`, and `npm run build`. The test suite includes an isolated mock-RPC Dry-run archive flow that verifies signal idempotency, partial fills, Freqtrade-owned exit, archive refresh, and restart persistence; it is contract evidence, not a connection to an exchange or a real Freqtrade deployment. Python tests in `npm test` use `.venv` (or the explicitly supplied `SBK1_PYTHON`). `GET /api/health` is SBK1's unauthenticated JSON health endpoint; an unauthenticated Freqtrade ping alone is not considered RPC health.
- Before upgrades, stop both services and back up the Freqtrade database configured by `db_url`, the private Freqtrade config, Freqtrade `user_data/`, the SBK1 signal outbox (default `data/freqtrade-signals.json`), and `database_kill_switch.json`. Verify a restore against copies before resuming. Keep the checked-in Freqtrade source at a reviewed upstream release; do not replace it with `develop` without compatibility tests.
- On an RPC failure, check the Freqtrade API is listening only on loopback, credentials match `FREQTRADE_USERNAME` / `FREQTRADE_PASSWORD`, and pair/timeframe/exchange configuration agrees across both processes. On a bridge failure, verify the same private token is set in both processes. The local supervisor requires loopback and the bridge fails closed on mismatches.
- If SBK1's signal JSON is invalid, do not delete or edit it to resume trading. Stop the services, preserve a copy for diagnosis, and restore from a verified backup or repair the record under review. The JSON store is single-process and is not safe as a multi-instance queue.
