# SBK1 + Freqtrade

SBK1 remains the TypeScript/React analysis and monitoring application. Freqtrade is the sole owner of exchange credentials, order placement, fills, open positions, stop-losses, exits, and trade persistence. The Node service validates a narrow, versioned SBK1 signal contract and provides an authenticated pull queue to a Freqtrade strategy. Signal generation is separate from execution; archived probabilities are informational, while the server runner requires verified calibration before producing candidates. Live execution remains disabled unless the owner explicitly sets `SBK1_LIVE_ENABLED=true` on the server and uses a guarded private Freqtrade configuration. The browser never calls the Freqtrade API.

This integration is **not declared production-ready**. The checked-in Freqtrade configuration is a dry-run template; no live exchange order, fill, restart recovery, or end-to-end deployment was executed in this workspace.

## Historical data and calibration status

- Audit real downloaded Freqtrade Feather OHLCV before backtesting with `.venv/bin/python scripts/audit_freqtrade_market_data.py freqtrade/user_data/data/bybit/futures/BTC_USDT_USDT-15m-futures.feather --timeframe 15m`. It checks timestamp order and cadence, missing intervals, finite values, OHLC geometry, future timestamps, and counts incomplete candles separately. It does not establish that historical order-flow features or SBK1 decisions are available.
- In the 2026-10-11 workspace audit, Bybit returned 35,109 BTC/USDT:USDT 15m candles from 2025-10-11 through 2026-10-11; the OHLCV audit found no gaps or malformed rows. Freqtrade's SbkSignalStrategy backtest on that history produced zero trades because the live external-signal queue is intentionally not consumed in backtesting. Zero trades is not a performance result.
- Browser `localStorage` is not a training source. The server-side operational archive stores runner decisions, contemporaneous feature snapshots, code/model/feature versions, lifecycle events, and closed-trade PnL/fees/exit reason from authenticated Freqtrade RPC, linked by signal ID and a positive trade ID. Only complete Freqtrade-confirmed outcomes enter probability training; the existing calibration engine still requires at least 40 training samples, 20 validation samples, and a dynamically sized out-of-sample set (at least 200), including both win and loss outcomes. Until these minima are met, the UI reports “نمونه ناکافی” and the server runner rejects entry candidates that lack verified calibration.
- Until enough timestamped SBK1 decisions, contemporaneous features, and authoritative Freqtrade outcomes are collected and validated, `/api/backtest/run` returns `HISTORICAL_SIGNALS_UNAVAILABLE`, the probability UI reports insufficient samples, and the server runner remains fail-closed for new entries.
- The 11-brain dashboard is only a registry of UI processor labels. Runtime health, votes, CPU, latency, and calibrated accuracy are not instrumented there and must not be inferred from its display.

## Signal and state ownership

1. SBK1 analysis produces a server candidate only when analysis allows it, the trigger is confirmed, market data is live/allowed, and the probability metadata is verified as calibrated. The signal-candidate branch is a gated candidate builder, not the full 14-stage UI decision pipeline; the order-flow sweep does not establish CVD divergence or calibrated probability.
2. `POST /api/hunter/execute` remains fail-closed for direct order execution. The managed server signal runner rejects candidates without verified calibration; Freqtrade remains the only order authority.
3. Authenticated polls to `GET /api/freqtrade/signals` serve valid production candidates only when Freqtrade is running with `force_entry_enable=false` and either `dry_run=true` or `SBK1_LIVE_ENABLED=true`. Live startup separately requires `dry_run=false` and non-empty exchange key/secret in the private config. For integration testing, `POST /api/freqtrade/dry-run-test-signal` remains restricted to the explicit fixture flag and Freqtrade `dry_run=true`.
4. Freqtrade strategy callbacks send status updates to `POST /api/freqtrade/signals/:signalId/status`; the admin-only `GET /api/hunter/signals/:signalId` is a signal audit view. Authenticated Freqtrade RPC `/status`, `/trade`, and paginated `/trades` are used for trading-state reads and closed-trade confirmation. Admin-only archive endpoints expose the server-side records.
5. `data/sbk1-operational-trade-archive.json` (overridable with `SBK1_TRADE_ARCHIVE_PATH`) is an atomic, restart-persistent SBK1 audit projection. It excludes test fixtures, stores the decision/features and code/model versions at signal creation, retains lifecycle-reported trade IDs and fill updates, and records PnL, fees, and exit reason only after authenticated Freqtrade RPC confirms the closed trade, matching signal tag, pair/direction, and valid trade ID. Every RPC snapshot is tagged `DRY_RUN` or `LIVE`; dry-run results remain simulations, not evidence of exchange fills. The archive is not a second trading database and never gates a trade. It is single-process/file-backed, so deployments must use one SBK1 writer and durable storage. Freqtrade's database remains the source of truth for trades, orders, balances and positions.
6. `UNKNOWN_IN_FLIGHT` signals remain visible to the strategy but quarantined from entry. After restart or a bridge timeout, the strategy reconciles the signal tag, pair, direction, and persisted Freqtrade order/fill state before advancing lifecycle; without an authoritative match it remains unknown and is never retried.

## Market-data and model truth policy

- Live OHLCV uses completed candles only. The Bybit and KuCoin readers validate finite OHLCV geometry, monotonic interval timestamps, and remove the still-forming candle; a missing interval or invalid timestamp rejects the feed. Candle event/close time, response receipt time, measured request latency, symbol, market type, and timeframe remain distinct.
- Bybit linear-futures `BTCUSDT` is primary. KuCoin `XBTUSDTM` can be used only after base asset, settlement, contract type, and timeframe compatibility checks pass. Spot, synthetic candles, and stale cache entries are never substitutes for live futures data. Failed or unproven provenance is unavailable, not zero or neutral.
- Price roles are not interchangeable: Last is the execution reference, Mark is the risk/stop/liquidation reference, and Index is the underlying benchmark. A missing required price is returned as unavailable; another price type is never substituted. Divergence cannot be considered safe unless both Last and Mark are fresh and valid.
- Order-book imbalance, Funding, Open Interest, and trade flow are valid only when the supporting live feed provides them with provenance. Unsupported or missing metrics remain unknown. Backtests must use only information available at or before each simulated event; use completed historical bars and do not forward-fill future values.
- `scripts/predictor.py` is a heuristic moving-average/price-change/order-imbalance analysis, not a trained or calibrated probability model. `scripts/garch_volatility.py` is a fixed-parameter, unfitted volatility approximation, not a validated forecast. Both explicitly return `tradeEligible: false`; missing input and process failures do not produce directional, confidence, regime, or target fallbacks. Their definitions are analysis-only and must not differ between backtest, dry-run, and live signal eligibility.
- Server analysis uses canonical OHLCV tuples in `[open, high, low, close, volume]` order; candle event timestamps remain separate metadata. Signal candidates require fresh, structurally valid Freqtrade market data, an allowed analysis result, a confirmed trigger, and verified calibration. Insufficient samples block new entries.
- MultiBrain widgets are diagnostic UI output and are not the server runner's independent order gate. Estimated CVD/OBI-derived features are labeled non-empirical, missing whale-transaction counts remain unavailable, and activity monitoring reports only recorded pulses without synthesizing health, latency, or restart status.

## Safety controls and order lifecycle

- SBK1 starts with its server-side kill switch engaged unless a valid persisted state says otherwise. Engaging it blocks new SBK1 signals, stops SBK1 auto-trade, and cancels unclaimed queued signals. It does **not** cancel exchange orders already submitted by Freqtrade or close/modify open positions; the API reports those as unaffected. Reconciliation and position management remain Freqtrade's responsibility. State is persisted in the ignored runtime file `database_kill_switch.json`.
- The mode endpoint accepts LIVE only when `SBK1_LIVE_ENABLED=true`; signal and status endpoints always require `force_entry_enable=false`. The optional dry-run fixture is a separate admin-only test path, refuses delivery unless Freqtrade RPC verifies `dry_run=true`, and never turns off Freqtrade's force-entry guard. Freqtrade's example config listens on loopback with authentication enabled and force-entry disabled. Never expose the Freqtrade management API publicly; configure credentials and permissions (withdrawal disabled and IP-restricted keys) only in the private Freqtrade deployment.
- Cross-origin browser access is denied unless the request is same-origin or its exact origin is listed in `SBK1_ALLOWED_ORIGINS`. Admin and bridge routes require server-side authentication. Keep `.env`, Freqtrade configuration, bridge tokens, and API credentials private.
- Order states are `CREATED → SUBMITTED → ACKNOWLEDGED → PARTIALLY_FILLED → FILLED`, with explicit `REJECTED`, `CANCELLED`, and `UNKNOWN_IN_FLIGHT` branches. Unknown submissions must be reconciled with Freqtrade/exchange before retry; repeated signal IDs are idempotent. Actual fill prices, fees, protective orders, orders, and positions are only confirmed from Freqtrade/exchange state, never from a local estimate.

The Node signal store is single-process and file-backed. Run one SBK1 writer, place the store on durable storage, and use a private network for the Node-to-Freqtrade bridge. Multi-instance deployments require a transactional shared store/queue before enabling this integration.

## Configuration and dry-run

1. Supply runtime-only configuration through your secret manager/service environment; do not commit `.env`, Freqtrade configs, passwords, JWT keys, bridge tokens, or exchange keys. Node needs `FREQTRADE_BASE_URL`, `FREQTRADE_USERNAME`, `FREQTRADE_PASSWORD`, `FREQTRADE_PAIR`, `ADMIN_TOKEN`, `SBK1_SIGNAL_EXCHANGE`, and `SBK1_FREQTRADE_TIMEFRAME`. `SBK1_LIVE_ENABLED` defaults to `false`; leave it false unless the owner deliberately enables live operation. Set `FREQTRADE__API_SERVER__USERNAME` and `FREQTRADE__API_SERVER__PASSWORD` to the **same values** as `FREQTRADE_USERNAME` and `FREQTRADE_PASSWORD`; the first pair configures Freqtrade's RPC server, while the second pair authenticates SBK1's RPC client. The `.env.example` lists both pairs. Freqtrade also supports `FREQTRADE__API_SERVER__JWT_SECRET_KEY`, `FREQTRADE__EXCHANGE__KEY`, and `FREQTRADE__EXCHANGE__SECRET` as environment overrides. Generate a random bridge token outside the repository and set the same value in `SBK1_FREQTRADE_BRIDGE_TOKEN` for Node and Freqtrade. `ADMIN_TOKEN` and the bridge token must each contain at least 32 characters. Never expose credentials to browser code. Do not configure exchange keys in SBK1; its guarded legacy exchange mutation routes return HTTP 410.
2. Copy `freqtrade_integration/config.example.json` to `freqtrade/user_data/config.json`; its RPC credential fields are intentionally blank and must be supplied through the matching `FREQTRADE__API_SERVER__USERNAME` and `FREQTRADE__API_SERVER__PASSWORD` overrides. Set `FREQTRADE_PAIR` and `SBK1_FREQTRADE_PAIR` to the same pair. The checked-in example stays at `dry_run: true`. The managed launcher accepts `dry_run: false` only when `SBK1_LIVE_ENABLED=true`, `force_entry_enable: false`, and both exchange key fields are non-empty in the private Freqtrade config. The launcher does not print credentials. Select LIVE through the authenticated server API; actual DEMO/LIVE status is read server-side from authenticated Freqtrade RPC, never from browser storage.
3. Export `SBK1_FREQTRADE_PAIR`, `SBK1_FREQTRADE_TIMEFRAME`, `SBK1_FREQTRADE_BRIDGE_TOKEN`, and `SBK1_BRIDGE_URL` into the Freqtrade process environment. These must agree with Node settings and the Freqtrade config. The strategy rejects remote HTTP bridge URLs and does not follow redirects while sending its token.
4. The managed launcher requires both APIs on loopback and the bridge/RPC credentials to match the private Freqtrade config. For a remote deployment, use a separately reviewed private-network/TLS deployment; the local launcher intentionally rejects remote cleartext URLs and non-loopback service bindings.
5. Validate in Freqtrade dry-run first. `npm run verify:freqtrade` is a read-only readiness probe and places no orders. SBK1's readiness diagnostic does not authorize live execution: calibrated probability evidence and real dry-run/exchange lifecycle verification remain unavailable.

In live/dry-run Freqtrade runmodes, the strategy pushes a versioned market snapshot to the private `POST /api/freqtrade/market-snapshot` endpoint at most every 10 seconds. The v4 contract carries completed DataProvider candles plus ticker, order-book, funding data, and recent public trades when the exchange's CCXT adapter supports `fetchTrades`. Recent trade flow is optional: unavailable, empty, or stale trades are marked unavailable, and only fresh trades may contribute to short-window CVD/taker-flow features; this is not cumulative historical CVD. The server runner hydrates its training dataset from the server-side operational archive, while only outcomes confirmed by Freqtrade RPC qualify as verified training examples. Ticker exchange-event time is distinct from the local time Freqtrade retrieved it; absent exchange time remains explicitly `null`, and only the retrieval time is used for short-lived freshness checks. Node authenticates the bridge token and cross-checks the running Freqtrade RPC exchange, market, pair whitelist, and timeframe before accepting a snapshot. Browser analysis consumes the snapshot through the SBK1 API and fails closed when required data is absent or stale. A managed Dry-run check confirmed RPC and 500 completed 15m candles, plus order book and funding. A separate read-only probe through Freqtrade's Bybit connector (CCXT 4.5.85) confirmed a positive ticker `last`, but both normalized `timestamp`/`datetime` and the raw Bybit ticker's top-level time were absent; Last/Mark/Index can therefore be marked as recently retrieved but have no exchange event timestamp. They must not be represented as exchange-timestamped data. Open interest and multi-exchange aggregation are still not supplied by this contract.

Fear & Greed is retrieved directly from `https://api.alternative.me/fng/` and is marked live only when its value and source timestamp pass validation. News, S&P 500, DXY, ETF flows, Fed expectations, economic-calendar events, and on-chain/whale metrics have no direct provider configured: their values remain `null`/`UNAVAILABLE`, with `NOT_CONFIGURED` provenance. Gemini and Google Search grounding are not used by the application. The economic-calendar endpoint returns unavailable instead of guessed recurring event dates and hard-coded forecasts. Direct provider adapters for the remaining metrics must be selected and configured before those fields can influence analysis.

The snapshot bridge does not enable production signal delivery by itself. Browser `localStorage` cannot choose an execution profile; the server mode endpoint allows LIVE only when the owner has enabled `SBK1_LIVE_ENABLED`, and status is derived from authenticated Freqtrade RPC. Signal and status paths require `force_entry_enable=false` and accept either dry-run or explicitly enabled live Freqtrade. The dashboard reads the Freqtrade balance, orders, fills, positions, signal lifecycle, kill switch, and fresh market snapshot without inventing values when RPC/data is unavailable. The orderflow snapshot and guarded dry-run fixture read the Freqtrade snapshot cache and fail closed when it is missing or stale. The server contains no direct Bybit connector or legacy private-order code. `npm test` includes an HTTP integration test that blocks all non-loopback fetches while proving legacy execution paths fail closed.

For a controlled integration exercise, set `SBK1_DRY_RUN_FIXTURE_ENABLED=true` only in the private Node environment, keep the Freqtrade config at `dry_run: true`, and verify `force_entry_enable: false`. Use the protected dashboard to verify RPC/configuration, disarm the SBK1 kill switch, then queue a test-only fixture; it uses a fresh Freqtrade DataProvider ticker, 1x leverage, a risk budget capped at 1% of the 100 USDT maximum stake, and no more than 100 USDT stake. Freqtrade RPC is checked when accepting snapshots, creating the fixture, and on each strategy poll. The checked-in configuration uses a fixed 100 USDT stake, one maximum open trade, and a 1,000 USDT virtual wallet; it never uses `stake_amount: unlimited`. Disable the fixture flag after testing. This verifies the bridge path only; it does not validate SBK1 model quality, live trading, or an exchange fill.

The fixture endpoint's `queued: true` / `executionStage: "QUEUED"` response means only that the signal was durably placed in the SBK1 queue. It is not evidence that the Freqtrade strategy accepted it, submitted an order, received a fill, or opened a position. The signal record separately tracks its receive time and lifecycle history; SBK1 queue actions and Freqtrade-reported transitions are labeled by source. Existing v1 signal-store records without that history are loaded compatibly with their recorded creation/update timestamps.

## One-command local startup

Follow the clean setup below, including `scripts/init_sbk1_config.py`; do not copy the blank configuration template directly over private settings. Run `npm run sbk1` from the repository root for the complete stack. The supervisor validates settings, confirms strategy discovery, starts the SBK1 API and then Freqtrade, and waits for authenticated RPC health before reporting readiness. It refuses conflicting listeners and never stops processes it does not own. Use `npm run sbk1:check` for non-starting validation and `npm run sbk1:status` for independent health reports. `npm run dev` starts only the SBK1 Node/Vite service and is not the full-stack command. If the default Node port is occupied, set `SBK1_PORT` to a free loopback port and leave `SBK1_BRIDGE_URL` empty so the strategy bridge follows that port. Both local APIs bind to loopback; remote deployment requires a separately reviewed private-network/TLS setup. If either managed child exits, the supervisor stops its other child; `Ctrl+C` gracefully stops both. SBK1 exposes `GET /api/health` as a JSON health endpoint.

The example targets Bybit USDT futures and `BTC/USDT:USDT`, because SBK1's current signal feed is a Bybit linear-futures feed. A different venue/pair requires matching SBK1 market data and Freqtrade configuration; mismatches fail closed. Spot shorts are rejected. The sample config cancels unfilled orders after 15 seconds; SBK1 signals expire after 45 seconds. The strategy also defines a 5% hard stop-loss ceiling as a fallback if its signal-specific stop cannot be recovered.

## Operating commands

- Start both services in dry-run mode: `npm run sbk1` from the repository root. The launcher refuses non-dry-run config and mismatched settings, reuses an already healthy matching stack without duplicating it, and refuses unhealthy/conflicting port listeners.
- Stop the managed stack with `Ctrl+C` in that terminal; the supervisor sends termination to both child processes. Do not kill a separately running process without identifying and coordinating with its owner.
- Check configuration/strategy discovery without starting services: `npm run sbk1:check`. Check live process health read-only with `npm run sbk1:status`.
- SBK1 logs are written to the startup terminal. Follow the Freqtrade log with `tail -n 100 -f freqtrade/user_data/logs/freqtrade.log`.
- Run tests with `npm test`; attempt production frontend build with `npm run build`; run the repository TypeScript check with `npm run lint`.

## Clean setup, backup, and upgrade notes

- Use a currently supported Node.js LTS release (Node.js 24 LTS is recommended; the checked-in Vite toolchain accepts Node.js 18, 20, or 22 and newer) and Python 3.12 or newer (Freqtrade declares `requires-python >=3.12`; Python 3.12 is the recommended reproducible baseline). Node.js 24.21.0 and Python 3.12.3 are the versions available for this validation:

  ```sh
  python3.12 -m venv .venv
  .venv/bin/python -m pip install --upgrade pip
  .venv/bin/python -m pip install -e ./freqtrade
  npm ci
  python scripts/init_sbk1_config.py
  npm run sbk1:check
  npm run sbk1
  ```

- The initializer reads `.env.example` and `freqtrade_integration/config.example.json`, checks that the exchange (`bybit`), futures market, pair (`BTC/USDT:USDT`), timeframe (`15m`), strategy (`SbkSignalStrategy`), and dry-run settings agree, then creates `.env` and `freqtrade/user_data/config.json` with mode `0600` on POSIX. It generates independent cryptographically random admin, bridge, RPC, and JWT credentials without printing them. It refuses to overwrite either private file; back up and reconcile existing settings manually. Review both private files, keep `dry_run: true`, and do not add exchange API keys for this local integration test. On Windows, use `py -3.12 -m venv .venv` and `.venv\Scripts\python.exe` / `.venv\Scripts\pip.exe`; restrict the private files' ACLs to the service account.
- The sample explicitly bounds fixture risk with `SBK1_SIGNAL_RISK_PCT=1`, `SBK1_SIGNAL_MAX_LEVERAGE=1`, and `SBK1_SIGNAL_MAX_STAKE_QUOTE=100`; Freqtrade's configured `stake_amount` is fixed at 100 USDT and `max_open_trades` is 1. The fixture's 1% risk is measured against its 100 USDT stake cap, not the full wallet. Review these controls before use. The optional fixture still requires `SBK1_DRY_RUN_FIXTURE_ENABLED=true`, fresh Freqtrade market data, authenticated RPC confirmation of dry-run, no open trades, force-entry disabled, and a disarmed kill switch. Turn the fixture flag off afterward. Production SBK1 signals remain disabled until calibrated-probability evidence and approved risk limits are available.
- `npm run sbk1` starts the complete managed stack: it validates private settings and strategy discovery, detects occupied ports, acquires a single-instance lock, starts SBK1 and Freqtrade, and waits for authenticated RPC health. `npm run sbk1:check` validates without starting services; `npm run sbk1:status` reports SBK1 API and authenticated Freqtrade RPC health separately. `npm run dev` starts only the SBK1 service. Ctrl+C requests graceful shutdown of both managed services. If either child exits unexpectedly, the supervisor stops the other and exits nonzero. Existing listeners are detected and never killed automatically; identify and authorize any stop yourself.
- After setup, validate with `npm test`, `npm run lint`, and `npm run build`. The test suite includes an isolated mock-RPC Dry-run archive flow that verifies signal idempotency, partial fills, Freqtrade-owned exit, archive refresh, and restart persistence; it is contract evidence, not a connection to an exchange or a real Freqtrade deployment. Python tests in `npm test` use `.venv` (or the explicitly supplied `SBK1_PYTHON`). `GET /api/health` is SBK1's unauthenticated JSON health endpoint; an unauthenticated Freqtrade ping alone is not considered RPC health.
- Before upgrades, stop both services and back up the Freqtrade database configured by `db_url`, the private Freqtrade config, Freqtrade `user_data/`, the SBK1 signal outbox (default `data/freqtrade-signals.json`), and `database_kill_switch.json`. Verify a restore against copies before resuming. Keep the checked-in Freqtrade source at a reviewed upstream release; do not replace it with `develop` without compatibility tests.
- On an RPC failure, check the Freqtrade API is listening only on loopback, credentials match `FREQTRADE_USERNAME` / `FREQTRADE_PASSWORD`, and pair/timeframe/exchange configuration agrees across both processes. On a bridge failure, verify the same private token is set in both processes. The local supervisor requires loopback and the bridge fails closed on mismatches.
- If SBK1's signal JSON is invalid, do not delete or edit it to resume trading. Stop the services, preserve a copy for diagnosis, and restore from a verified backup or repair the record under review. The JSON store is single-process and is not safe as a multi-instance queue.
